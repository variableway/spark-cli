一、lucid 的总体思路

lucid 是「用代码写视频」的引擎。画面不是拖模板拼出来的，是写一段 JavaScript： 第 t 毫秒这一帧该长什么样，由代码算出来。

SHOT.S03 = function (ctx, t, S) { … }

引擎负责逐帧渲染、拼片、混音、体检和交付核对； 片子好不好看，取决于写镜头的人。下面五条是它的总体思路。

1画面只由时间算出

镜头只依赖 t，不存状态、不用随机数——所以能逐帧渲染、分段并行、只重渲改过的镜头。

lint.py 渲染前拦违规写法

2代码就是分镜

引擎给的是一套排版与运动的词汇表。写镜头＝登记物件→分区→放主体→出字→登记事件。

engine.md · explainer/promo/review.md

3时间轴决定一切

beats / manual / voice 三种模式。讲解片用 voice，画面事件挂在短句上，声音天生对齐。

timeline.py 同步时间线；tts.py full 合成并转写

4草稿迭代，正式档一次

草稿半尺寸、快；正式档开运动模糊，并跟草稿逐帧比对查重影。

render.py 默认草稿／--final 正式；分段指纹决定增量

5验收靠机器

渲染前预检三道，渲染后体检；硬伤拦住渲染，可选提示只写进报告。

lint.py → 页面预检 → layout.py；checkup.py 体检

三、终端素材从哪来

图 2 · 画面里那些终端输出不是画的，是真的跑出来的。 profile 声明要录哪条命令，录制器把它执行一遍、按参数渲染成无损 PNG 帧序列， 帧序列旁边的 meta.json 写下最终分辨率下的真实网格，镜头代码再把这四个数抄过去。 124 帧，全部来自 4 条真实命令。

素材实际执行的命令帧数时长尺寸
help/Users/patrick/innate/innate-apps/spark-cli/bin/spark --help906.03 秒1250×776
version/Users/patrick/innate/innate-apps/spark-cli/bin/spark version342.266 秒1250×262
repo00 秒0×0
skill00 秒0×0
名义列宽1250 ÷ 92 = 13.5870 px
真实列宽meta.json 的 cell.cw = 13.1803 px
差 3.0%用名义值，标注线会整体偏掉

素材文本区两侧留了内边距（1250px 宽里文字只占 1212.585px）， 所以真实列宽不等于「画幅宽 ÷ 列数」。 check_crop.py 会拿镜头代码里的几何常量跟 meta.json 逐个比对 （容差 0.02 像素），对不上就拦住渲染——所以别手算，抄 meta.json。

四、原件与工作副本

图 3 · skills/lucid/template/ 是 lucid 框架的原件，project/ 是它的工作副本。两边同名文件里 44 个逐字节相同，只有 3 个不同；工作副本独有的 170 个文件里，只有 1 个是手写的（web/shots_spark.js），其余都是录制、时间线、配音这些工具的产物。所以框架升级时可以整目录覆盖，只需要把 3 个手写文件搬回去。
